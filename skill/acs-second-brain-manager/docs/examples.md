# 公考行业使用案例

这些例子用于帮助非技术用户理解 Skill 的行为，不代表固定目录或行业模板。

## 1. 同行交流记录

用户：

> “我今天和某机构负责人聊了一个小时，帮我入库。”

正确流程：

1. 保留原始交流记录；
2. 查找该机构是否已有实体页；
3. 查找讨论到的渠道、产品、师资或运营方法是否已有知识页；
4. 判断 UPDATE / MERGE / CREATE / PENDING / SOURCE_ONLY；
5. 先给方案；
6. 用户确认后写入。

不应该把整段聊天直接复制到一个新页面后就结束。

## 2. 老师去向发生变化

用户：

> “某老师现在去了 B 机构。”

如果已有该老师实体页，应优先 `UPDATE` 人物当前状态，并检查原机构与新机构关系。

如果来源只是传闻，则标记待核，不能写成已确认事实。

## 3. 用户经营观点变化

用户：

> “我现在越来越觉得渠道先行比先开分校更重要。”

这是 `User Judgment`，不是行业客观事实。

如果原来已有相反判断，应分析这是补充、条件变化还是明确替代；不能只在页面底部加“最新观点”。

## 4. 收到一份机构财报

财报属于 Source Layer。

正确做法：

- 原始 PDF 不改；
- 提取营收、成本、业务线等可追溯事实；
- 事实带统计期间；
- 分析判断与事实分开；
- 如已有机构页和财务研究页，优先合并。

## 5. 班级项目问题持续记录

如果项目已经有 tracker / 问题闭环台账，新问题应更新台账当前状态，而不是每一个问题建立一篇独立知识页。

项目是否结束不能由 Agent 根据日期自动判断。

## 6. 查询历史判断

用户：

> “我以前怎么看加盟模式？”

这是 Retrieve，不是 Mutation。

Agent 应找到相关知识页和必要来源，读取足够上下文后回答；不能因为“顺手”修改知识库。

## 7. 两条招生数据冲突

来源 A：800 人。

来源 B：1200 人。

如果无法核验，应 `PENDING`，说明两个来源各自支持什么，不替用户猜一个数字。

## 8. 同一机构多个叫法

知识库里可能有：

- 某机构正式名；
- 简称；
- 公司主体名；
- 创始人 IP 名称。

Skill 应先做实体核对，不能只按字符串合并。

## 9. 一份资料暂时没必要提炼

有些会议附件或宣传材料未来可能有用，但当前没有形成可复用知识。

可以选择 `SOURCE_ONLY`：保存原件，先不新建知识页。

## 10. 做一次行业资料体检

用户：

> “看看我机构研究这块有没有重复和混乱。”

健康检查默认只读。可以找：

- 同名页面；
- 断链；
- 重要结论没来源；
- 同主题多个碎片页；
- 旧快照被误当当前事实；
- 人物/机构关系冲突。

报告后再由用户决定修哪些。
