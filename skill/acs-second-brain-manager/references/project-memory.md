# 专项记忆规范

专项记忆是长期项目的结构化接手文件。它让用户或 Agent 在换新对话后快速恢复项目定义、当前状态、关键决策和下一步，而不必重新回放整段聊天历史。

## 1. 适用与不适用

适合建立专项记忆：

- 项目需要跨多次对话持续推进；
- 工作会跨越多天或多周；
- 已出现多个关键决策，后续需要复用决策理由；
- 项目有明确阶段、卡点、文件和交付物；
- 新对话需要快速接手，而不能依赖完整聊天历史。

通常不需要：

- 一次性文章、图片或简单文件转换；
- 当前上下文足以完成的短任务；
- 只有零散想法、尚未形成项目的事项；
- 已由项目页或任务台账完整承载，且没有跨会话接手需求的简单项目。

发现长期协作需求时，可以建议建立专项记忆；未经用户授权，不自动创建或写入。

## 2. 命名

推荐格式：

```text
[项目简称] 专项记忆.md
```

文件名使用易输入、易搜索且不会与其他项目混淆的简称；文件内一级标题写完整项目名。

如果知识库已有其他命名规则，应优先遵循现有规则，不为了套用本规范批量重命名。

## 3. 内容结构

可直接复制 [`../templates/project-memory.md`](../templates/project-memory.md)。核心结构分为：

1. **项目定义**：定位、范围、成功标准、策略、长期目标；
2. **当前状态**：一句话状态、当前阶段、项目级卡点；
3. **当前文件结构**：根目录、关键文件、交付物和来源入口；
4. **专项特有规则**：仅记录这个项目独有且会改变执行方式的约束；
5. **进展**：最近完成、正在进行、下一步；
6. **关键决策**：决策内容、原因和影响；
7. **关键文件**：引用权威文件，不复制其正文；
8. **归档索引**：链接历史归档并概括其覆盖范围。

字段可以按项目实际情况裁剪。不要为了填满模板制造未知信息、空章节或虚假进度。

## 4. 与项目页、任务台账和日志的分工

专项记忆不是所有项目数据的唯一容器。

| 载体 | 主要职责 |
| --- | --- |
| 专项记忆 | 项目级定义、当前阶段、关键决策、卡点、接手入口和重点链接 |
| 项目页 | 稳定背景、长期说明、对外可读的项目知识 |
| 任务台账 | 逐项动作、负责人、期限、状态、验收和复测 |
| 工作日志 | 按时间记录发生过的操作或事件 |
| 原始材料 | 保存原始证据和完整上下文 |

如果已经有任务台账，专项记忆中的“进行中”和“下一步”只保留项目级目标、重大依赖与台账链接，不重复维护每条任务。简单项目可以只用项目页。

## 5. 内容原则

应记录：

- 项目目标、范围、成功标准和核心策略；
- 当前阶段、真实卡点和最近发生的实质变化；
- 关键决策及其理由、影响；
- 重要发现、失败原因和可复用教训；
- 具体、可验证的下一步；
- 本项目特有的执行约束；
- 能帮助新对话快速定位现场的权威文件链接。

不应记录：

- 每日流水账和详细执行过程；
- 已在规划、台账或来源文件中完整存在的大段重复内容；
- 尚未确认的临时想法和讨论过程；
- 把推测写成确定状态；
- 密钥、访问令牌、个人证件号、私人联系方式等敏感数据；
- 不必要的本机用户名、绝对路径、客户名或内部系统标识。

对身份、金额、日期、归属等关键事实无法确认时，明确标记“待核”，不要猜测补齐。

## 6. 维护规则

### 只在发生实质变化时更新

适合更新的时机：

- 用户作出关键决策；
- 当前阶段、卡点或下一步发生变化；
- 一个阶段完成；
- 出现会改变后续执行的重要问题或规则；
- 准备结束一次确有实质变化的协作，需要为下次接手同步状态。

只读问答、没有状态变化的讨论或单纯重新查看文件，不应为了“留痕”而写入。

### 500 行软上限

专项记忆建议控制在 500 行以内。超过时先压缩，不在第 501 行机械拆分：

1. “已完成”只保留最近且仍有接手价值的条目，通常不超过 10 条；
2. 把旧决策移入归档，主文件只保留索引和仍有效的结论；
3. 重写一句话状态，删除过时描述；
4. 删除低价值过程信息和重复内容。

压缩后仍过长，且旧内容确实妨碍接手时，再归档。

推荐归档命名：

```text
归档/专项记忆-历史-YYYYMM.md
```

归档保留有复用价值的决策理由、失败原因和重要试错；纯重复讨论、无价值临时过程可不保留。主文件应留下归档链接和一句话摘要。

## 7. AI 协作者使用规则

### 创建

- 用户明确要求创建，或用户批准的方案已包含创建时，才写入；
- 首次发现项目可能长期持续时，可以说明价值并建议建立，但不能把用户是否同意当作继续当前任务的前置条件；
- 创建前检查现有项目页、任务台账或同名记忆，避免建立第二套真相源。

### 恢复上下文

跨会话恢复长期项目或当前上下文不足时：

1. 根据项目名、文件路径或索引精确定位对应专项记忆；
2. 只读取与当前任务相关的一份，不扫描所有项目记忆；
3. 同一连续任务中，文件未变化时复用已读内容；
4. 结合当前现场文件继续执行，现场事实优先于旧记忆；
5. 专项记忆记录的旧授权不能替代用户对当前写入或外部操作的授权；
6. 记忆缺失但上下文足够时继续工作；只有关键历史决定无法核实时，才询问最小必要信息。

### 更新

- 先确认用户已授权当前写入范围；
- 读取当前完整文件和相关现场来源，再做语义更新；
- 同一批变化集中维护一次，避免多次并发改写同一文件；
- 更新后复核日期、当前状态、下一步、链接和待核项是否一致。

## 8. 隐私与公开发布

专项记忆往往包含比普通说明文档更密集的内部信息。公开模板可以发布，真实项目记忆通常不应直接公开。

公开前至少检查并替换：

- 姓名、手机号、邮箱、账号和个人身份信息；
- 客户、学员、员工、合作方及未公开项目名称；
- 本机用户名、绝对路径、内网地址和系统标识；
- 密钥、Token、Cookie、仓库凭证及访问方式；
- 未公开金额、合同条款、经营数据和内部判断；
- 只能由内部治理文件解释的 Agent 名称、权限和协作机制；
- 能通过文件名、链接或示例反推出真实业务的信息。

脱敏不是简单删除姓名。应把真实对象替换为通用占位符，并再次检查上下文能否间接识别主体。

## 9. 验收标准

一份合格的专项记忆应让新的协作者在读完后，能回答：

1. 这个项目是什么、不是什么？
2. 现在处于哪个阶段？
3. 当前最大的卡点是什么？
4. 哪些决策已经确定，为什么？
5. 哪些文件是现场权威来源？
6. 下一步具体做什么？
7. 哪些信息仍然待核？

如果只能看出“做过什么”，却看不出“为什么、现在怎样、下一步是什么”，它仍然是一份日志，不是合格的专项记忆。
