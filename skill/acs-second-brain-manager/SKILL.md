# 第二大脑知识库管理器

当前版本：`v1.0`。

本 Skill 的目标不是替用户建立一套固定目录，而是先理解用户自己的知识库，再按该知识库已经确认的规则长期治理。

核心方法：

1. **Adaptive Structure**：先理解已有结构，再适配；已有库默认不重构。
2. **Immutable Source**：原始材料默认保持原样，可追溯，不静默改写。
3. **Living Knowledge**：知识页维护当前最清晰、最可继续使用的版本，不堆叠聊天流水。
4. **Read ≠ Write**：查询、分析、健康检查默认只读；写入需要明确授权。
5. **Evidence Boundary**：区分来源事实、用户判断、Agent 推断、用户决策和未知/待核。

## 适用范围

适合：

- 本地 Markdown 文件夹；
- Obsidian Vault；
- 以 Markdown 为主要知识页、同时保存 PDF / Word / 图片 / 表格等原始资料的个人或团队知识库；
- 用户希望 AI 长期维护“当前可用知识”，而不是只做一次性摘要。

不负责：

- 纯网页抓取、公众号正文提取、在线 PDF 下载；这类任务优先交给专门的 ingest / browser Skill；
- 普通写作、代码、网页搜索；
- 没有知识库上下文的泛问答；
- 未经授权的大规模目录重构、删除、批量移动或实体合并。

## 第一次使用：先完成 Onboarding

只补齐用户尚未给出的信息，不机械重复提问。

### 1. 确认知识库根目录

如果用户已经明确当前工作区就是知识库，先验证；否则询问知识库根目录。

必须确认路径存在并可读取。不得使用开发者路径、历史用户路径或模型记忆猜测。

### 2. 判断已有库还是新库

- **已有知识库**：进入 Read-only Adaptive Scan。第一次扫描不得新建、移动、重命名或删除任何知识库文件。
- **新知识库**：先询问主要用途与内容类型，再提出最小结构方案；用户确认后才初始化。不得默认复制任何特定个人或行业目录。

### 3. 确认写入模式

默认推荐 `confirm-first`：先分析、查重、给完整写入方案，用户确认后在该方案范围内端到端执行。

支持：

- `read-only`：只查询、分析、诊断、给建议；
- `confirm-first`：默认；
- `trusted-task`：用户确认一次任务边界后，可在该边界内连续维护；治理规则变化和高风险动作仍需单独确认。

详细流程见 [onboarding.md](references/onboarding.md)。

## 已有库首次接管：Adaptive Scan

优先运行或等价执行 `scripts/scan_knowledge_base.py`，只读识别：

- 一级、二级目录和主要业务域；
- `AGENTS.md`、README、结构说明、索引、日志、状态文件；
- frontmatter 习惯和常用页面类型；
- Wiki Link / Markdown Link；
- 原始资料目录与知识页目录；
- 项目、归档、专项记忆或持续台账；
- 已有脚本、自动化和多 Agent 协作痕迹。

扫描结果只是**观察**，不是已确认规则。

先输出 `Knowledge Base Understanding Report`，明确：已确认、推断、冲突、未知、建议沿用规则。得到用户确认后，才创建或更新库内治理层。

## 库内治理层

默认治理目录：

```text
.second-brain/
├── profile.yaml
├── structure-contract.md
├── state.json              # 仅在确有运行状态/并发需要时创建
└── governance-log.md       # 仅在需要记录治理变更时创建
```

`.second-brain/` 属于治理层，不属于业务知识层：

- 不进入知识索引；
- 不计入知识页数量；
- 不作为业务主题节点参与普通知识检索；
- 不存放人物事实、项目结论、行业研究或用户观点。

如果知识库已经有等价的 `AGENTS.md`、结构约定、日志或状态文件，优先复用，不制造第二套真相源。

### 权威顺序

发生冲突时，按以下顺序处理：

1. 用户在当前任务中的明确指令；
2. 用户已有且明确声明为权威的 workspace / governance 规则；
3. 已确认的 `.second-brain/structure-contract.md`；
4. `.second-brain/profile.yaml` 中的机器配置；
5. 扫描推断出的模式。

自动推断永远不能覆盖明确规则。

## 知识查询：默认只读

用户问“我以前怎么看”“这个项目现在什么状态”“某人和谁有关”时：

1. 先按明确标题、文件名、别名、实体名定位；
2. 找到入口后优先读命中页相关章节；
3. 需要时沿真实来源和关联页扩展；
4. 定位失败才逐步扩大搜索；
5. 只有全库审计、完整清单或健康检查才做大范围扫描。

不得只凭孤立命中行得出结论；必须读取足够上下文。

查询完成不会自动产生写入。详细见 [knowledge-model.md](references/knowledge-model.md)。

## 新资料入库：五种 Mutation Decision

任何新知识写入前，先读源、找相关页、查重、检查冲突、判断来源边界，再给 Mutation Plan。

最终只允许五类处理：

| 系统动作 | 中文含义 | 典型情况 |
| --- | --- | --- |
| `UPDATE` | 更新已有知识 | 新事实明确替代旧状态 |
| `MERGE` | 合并进已有内容 | 新资料属于已有主题或模块 |
| `CREATE` | 新建知识页 | 确实形成新的实体、概念、项目、案例或流程 |
| `PENDING` | 暂时待核 | 关键事实冲突或身份、金额、日期等无法确认 |
| `SOURCE_ONLY` | 只保存原始资料 | 原件值得保留，但暂时不值得提炼成知识页 |

默认 `confirm-first` 下，方案至少说明：

- 推荐分类与路径；
- 更新/合并/新建/待核/仅留原件；
- 来源如何保存；
- 哪些旧结论会被覆盖；
- 是否有事实冲突；
- 是否建立或更新实体关系；
- 是否影响索引、项目状态或治理规则。

用户批准完整方案后，授权覆盖该方案范围内必要的关联页、索引和收尾；不得扩大到未批准的治理变更或无关页面。

## Living Knowledge：知识页维护当前版本

知识页不是聊天流水。

- 新结论明确替代旧结论：更新旧口径；
- 新信息属于已有主题：合并到对应模块；
- 真实冲突尚未解决：并列保留并标记冲突；
- 历史讨论由原始材料、日志或必要快照承担；
- 不按“第几次讨论”“谁说的”“最新补充”机械新增章节。

回写后检查重复、标题层级、阅读顺序、待定状态和来源关系。

## 原始材料与知识页分层

默认采用 Source Layer / Knowledge Layer：

- **Source Layer**：原始 PDF、Word、聊天导出、网页快照、会议原文、用户口述原始记录等；默认不改写、不覆盖；
- **Knowledge Layer**：可提炼、合并、更新的当前知识。

如果已有库没有原始材料层，不自动创建；先向用户说明价值和迁移成本，给方案后再决定。

已有源文件不得为了“整理”被静默改写。复制或移动原件属于较高风险，应保留文件名、来源和必要的完整性校验。

## 事实边界

重要内容应区分：

- `Source Fact`：来源直接支持；
- `User Judgment`：用户明确表达的判断；
- `Agent Inference`：Agent 基于多条信息形成的分析；
- `Decision`：用户明确拍板；
- `Unknown / Pending`：当前无法确认。

不得把用户观点写成客观事实，也不得把 Agent 推断伪装成来源事实。

## 页面类型

如果用户已有页面类型体系，遵循现有规则。

没有时，可推荐以下通用语义类型，但不得强制改变物理目录：

- `entity`：人物、机构、产品、项目、业务线；
- `concept`：概念、方法论、模型；
- `source-summary`：单一来源摘要；
- `comparison`：多对象对比；
- `synthesis`：跨来源综合判断；
- `case`：案例；
- `procedure`：流程/SOP；
- `tracker`：持续维护状态的台账。

**type 描述页面性质，不决定目录。**

## 实体与关系

遇到同名、简称、别名、曾用名或人物—机构关系：

1. 先识别潜在别名；
2. 比较上下文与来源；
3. 有歧义时不给自动合并；
4. 形成 Merge Proposal；
5. 重大歧义由用户确认。

只在关系对导航和理解有稳定价值时建立链接；不机械补满返链。

## 时效知识与快照

排名、价格、人数、粉丝量、项目状态、当期市场数据等必须记录观察日期或统计期间。

`updated` 只是文件修改时间，不能替代数据发生时间。

长期方法与当期数据分开；方法不变时保留长期页，时效数据用快照。只有至少两期同口径数据才可称“趋势”。

## 项目状态

不得仅凭日期、沉默时间或 Agent 推断把项目标为已结束。

优先依据：

1. 用户明确确认；
2. 已有项目状态字段；
3. 知识库已确认的项目治理规则。

无法确认时标记待核。

## 健康检查

“检查知识库”“做体检”等触发只读 Health Check。可运行 `scripts/health_check.py` 获取结构信号，再由 Agent 做语义审查。

检查至少考虑：

- 重复文件名/疑似重复实体；
- 断链；
- 孤立页；
- 索引遗漏或重复；
- 重要事实缺来源；
- 过期快照；
- 项目状态矛盾；
- 同主题碎片化；
- frontmatter / 命名 / 路径漂移；
- 原始材料异常风险。

脚本只报告结构信号，语义冲突和实体等价必须由 Agent 复核。

健康检查默认只报告，不自动修复。详细见 [health-check.md](references/health-check.md)。

## 治理变更属于高风险

以下不能被普通“帮我入库”授权顺带执行：

- 一级目录新增、删除、重命名；
- 大规模移动或批量重命名；
- 页面类型体系变化；
- 模板、索引机制、来源策略变化；
- 修改 `profile.yaml` 或 `structure-contract.md` 的治理含义；
- 开启/改变多 Agent 写入机制；
- 大规模实体合并；
- 删除文件。

先说明影响、回滚路径和迁移范围，得到明确确认后执行。

## 并发与多 Agent

默认 `single-agent`。

用户确有多个 Agent 同库协作时才启用 `multi-agent`，原则是：multiple readers + single writer。使用写锁、任务所有者、handoff 和故障接管，接管只能继承原授权，不得扩大任务范围。

见 [concurrency-policy.md](references/concurrency-policy.md)。

## 收尾

写入完成后至少回报：

- 更新了什么；
- 新建了什么；
- 合并了什么；
- 哪些旧结论被覆盖；
- 哪些继续待核；
- 哪些只保存为原始材料；
- 是否更新索引/关系/项目状态；
- 校验结果与未解决问题。

不要只回复“已入库”。

## 最终安全原则

1. 先理解，再治理。
2. 先读源，再写知识。
3. 查询不等于写入。
4. 已有规则优先于自动推断。
5. 原件默认不可变。
6. 关键冲突不猜。
7. 不为“整齐”制造无意义页面和链接。
8. 不把开发者自己的目录、身份、路径或业务模型强加给用户。
