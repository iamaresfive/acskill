# 第二大脑知识库管理器

`acs-second-brain-manager` 是一个面向本地 Markdown / Obsidian 知识库的 AI 管理 Skill。

你可以把它理解成：**一个长期帮你管理电脑知识库的 AI 管家。**

它不是把所有文件塞进一个文件夹，也不是把每次聊天复制进去。它会先理解你原来的目录和整理习惯，再帮你做查询、入库、更新、合并、来源追踪和知识库体检。

## 一句话理解

> 原始材料负责保留“当时到底说了什么”，知识页负责维护“我们现在对这件事到底怎么看”。

这是整个 Skill 最重要的设计。

## 最适合什么人

尤其适合已经积累很多资料、但开始遇到这些问题的人：

- 文件越来越多，半年后找不到；
- 同一个机构、老师、项目有多个页面；
- 每次让 AI 总结都会重新从头读；
- 旧结论和新结论混在一起，不知道哪个是当前版本；
- Word、PDF、会议记录很多，但没有形成可持续复用的知识；
- 想让 AI 长期管理资料，又担心它把目录改乱或把事实写错。

公考培训机构负责人、项目负责人、行业研究者、自媒体运营者、咨询顾问都可以使用；但它并不绑定公考行业。

## 它不是什么

### 不是网盘

它不追求“把文件都存进去”，而是治理文件与知识之间的关系。

### 不是聊天记录仓库

用户问了一次问题，不等于要把这次聊天写进知识库。

### 不是自动改目录软件

第一次接管已有知识库时默认只看不改，不会一上来给你重建目录。

### 不是必须使用 Obsidian 的插件

Obsidian 很适合这套方法，但普通 Markdown 文件夹也能用。

### 不是自动把 AI 推断当事实

系统要求区分来源事实、用户判断、Agent 推断、用户决策和待核信息。

## 为什么要把“原始材料”和“知识页”分开

假设你拿到一份：

`某公考机构2026年内部交流纪要.docx`

推荐的处理方式不是改这份 Word，而是：

```text
原始材料
└── 某公考机构2026年内部交流纪要.docx   ← 保留原文

知识页
├── 机构-某机构.md                       ← 当前机构认知
├── 公考机构渠道模式.md                   ← 可复用方法论
└── 班型运营模式对比.md                   ← 跨机构综合判断
```

原始材料回答：

> “当时别人到底说了什么？”

知识页回答：

> “基于现有资料，我们现在对这件事到底怎么看？”

即使半年后你的判断变化，原件仍然可追溯；知识页则更新成当前最可用版本。

## 为什么知识页不能一直往后追加聊天记录

比如第一次得到的信息是：

> 某机构计划开 5 个教学点。

后来确认：

> 最终只落地 3 个。

如果知识页一直这样堆：

```text
3月：计划5个教学点
5月：可能调整
7月：最终3个
```

半年后人和 AI 都要重新判断哪个才是当前状态。

更好的方式是：

**当前知识页**

> 2026 年最终落地 3 个教学点。

**原始材料 / 历史记录**

仍然保留“最初计划 5 个”的来源。

这就是 `Living Knowledge`：知识页维护当前版本，历史由来源和必要快照承担。

## 第一次使用会发生什么

如果你已经有一个 Obsidian Vault 或 Markdown 知识库，第一次接管默认：**只看，不改。**

大致流程：

```text
确认知识库位置
↓
扫描目录与治理文件
↓
识别命名、frontmatter、索引、双链、原始资料、项目结构
↓
输出“我对你这个知识库的理解”
↓
你确认或纠正
↓
建立/复用库内治理配置
↓
以后按这套规则工作
```

不会默认把你的目录改成 `People / Projects / Topics`，也不会复制开发者自己的目录。

详细步骤见 [5分钟快速开始](docs/quick-start.md)。

## 知识库配置档案（Profile）是什么

第一次出现 `Profile` 这个词时，不需要把它理解成“用户画像”。

它就是：**这套知识库的设置表。**

默认文件：

`.second-brain/profile.yaml`

它记录例如：

- 这个知识库叫什么；
- 是 Obsidian 还是普通 Markdown；
- 哪些目录是知识，哪些是原始资料；
- 使用双链还是 Markdown 链接；
- 入库前要不要确认；
- 是否开启多 Agent 协作；
- 哪些规则文件具有最高权威。

## 知识库结构与治理约定是什么

默认文件：

`.second-brain/structure-contract.md`

可以把它理解成：**这套知识库的管理制度。**

Profile 偏参数，Structure Contract 偏规则。

例如它会说明：

- 什么内容放哪里；
- 什么情况新建页面；
- 什么情况更新旧页面；
- 文件怎么命名；
- 项目什么时候能归档；
- 来源怎么记录；
- 哪些动作必须先确认。

## 为什么治理文件放在知识库内部

默认结构：

```text
.second-brain/
├── profile.yaml
├── structure-contract.md
├── state.json
└── governance-log.md
```

这样整个知识库复制到另一台电脑后，规则也一起走。

但 `.second-brain/` 不是业务知识区：人物、机构、项目结论、行业研究都不能偷偷塞进去。它只放治理配置、规则、状态和治理日志。

如果你的库已经有 `AGENTS.md`、结构约定或其他成熟规则，Skill 会优先复用，不会强制再造一套。

## 入库时系统会做什么

新资料不会直接写。

先判断属于哪一种：

| 系统动作 | 你可以怎么理解 |
| --- | --- |
| `UPDATE` | 更新已有知识 |
| `MERGE` | 合并进已有内容 |
| `CREATE` | 新建知识页 |
| `PENDING` | 暂时待核 |
| `SOURCE_ONLY` | 只保存原始资料 |

### UPDATE：更新已有知识

例如：

> 某老师已经从 A 机构去了 B 机构。

优先更新现有实体，而不是新建“某老师最新情况.md”。

### MERGE：合并进已有内容

例如你又得到一个“加盟模式”的案例。

如果已经有“加盟模式”知识页，通常合并进去，而不是创建“加盟模式补充2”。

### CREATE：新建知识页

只有确实出现新的实体、概念、项目、流程、案例等，才新建。

### PENDING：暂时待核

比如两份资料的招生人数不同，系统不会帮你猜一个。

### SOURCE_ONLY：只保存原始资料

有些资料值得留档，但当前没有必要提炼成独立知识页。

## 为什么入库前要确认

因为知识库和普通聊天不同。

聊天里一句错误回答，影响通常有限；一旦错误信息写进长期知识库，以后的 AI 可能不断引用它。

因此系统会特别谨慎处理：

- 人名和机构身份；
- 金额；
- 日期；
- 项目状态；
- 事实冲突；
- 大规模目录调整；
- 实体合并和删除。

默认模式是：**先给完整方案，确认一次，然后在批准范围内执行。**

## 最常用的 10 句话

不需要背命令，直接这样说即可：

1. “把这个入库。”
2. “先看看应该放哪里，不要写。”
3. “更新一下这个机构的信息。”
4. “这条跟我以前的观点有没有冲突？”
5. “把这几份资料合并进现有知识。”
6. “我以前怎么看这个问题？”
7. “这个人物跟哪个机构有关？”
8. “检查这个项目现在是什么状态。”
9. “帮我看看知识库有没有重复内容。”
10. “做一次知识库健康检查。”

## 公考行业怎么用

这个 Skill 本身是通用的，但公考行业特别适合使用，因为资料天然分散在：同行交流、课程项目、老师/IP、机构动态、政策、真题、经营数据和用户判断中。

例如：

- 同行交流记录：保留原文，再更新机构页和方法论；
- 老师流动：更新人物—机构关系；
- 经营观点：明确标成用户判断，不写成行业事实；
- 财报：原始报告不改，提取可追溯事实和战略判断；
- 项目问题：更新当前 tracker，而不是不断创建零散问题页；
- 历史查询：“我之前怎么看加盟？”只查询，不自动写入。

完整案例见 [公考行业使用案例](docs/examples.md)。

## 健康检查是什么

可以直接说：

> “检查一下我的知识库。”

默认只读，检查结构信号和需要人工复核的问题，例如：

- 重复页面；
- 断链；
- 孤立页；
- 索引遗漏；
- 重要事实缺来源；
- 项目状态矛盾；
- 同主题碎片化；
- 过期快照；
- 命名和结构漂移。

健康检查只报告，不自动批量修复。

## 新手和专业用户都能用

新手只需要掌握：

> 给资料、提问题、看方案、确认。

专业用户还可以进一步使用：

- frontmatter；
- Entity Resolution；
- Snapshot；
- Source Traceability；
- Multi-Agent single-writer；
- 自定义治理规则。

术语解释见 [概念解释](docs/concepts.md)。

## 安全边界

默认不会：

- 删除你的文件；
- 改写已有 PDF / Word 原件；
- 因为“看起来过期”就把项目自动归档；
- 因为名字相同就自动合并人物或机构；
- 因为你问了一次问题就写知识库；
- 第一次打开已有库就重构目录。

高风险治理变化必须单独确认。
